# Native flight route contract — preimplementation

Source review: generated Minecraft1.21.1 Parrot constructor installs FlyingMoveControl(this,10,false). Its MOVE_TO branch enables native noGravity, turns yaw by at most90 degrees/pitch by maxTurn, chooses ground MOVEMENT_SPEED or airborne FLYING_SPEED, and supplies native forward/vertical input. Its WAIT branch disables noGravity when hoversInPlace is false. Parrot inherits LivingEntity travel; Parrot.aiStep subsequently scales downward velocity by0.6 during flapping. These are actual controller/travel rules, not creative/player flight.

Proposed first exact mode is an awake, nonsitting dry Parrot with the reviewed controller and collision-enabled body. Other native flyers remain pending. Do not infer support for Bee, Allay, Vex, Phantom, Ghast, Bat or custom controllers from a shared class name. No native navigation search, target invention, velocity assignment or full AI tick. Native component preparation may change gravity/input; failures afterward are terminal, never a pre-start rejection or retry.

Proposed guest contract (requires native implementation review before enabling): locomotion flying, physics native-parrot-flight-post-tick, flightTargetYOffset=max(.05,(1-height)/2), canFly true, jump/parkour disabled. Raw selected nodes remain integral feet cells. Physical target is x/z center and y+offset. Three-dimensional adjacent horizontal/diagonal/up/down edges require loaded swept actual body/eye geometry, collision shapes, policies and entity exclusions; no ground support or liquid traversal. Unknown cells are unavailable. Direct shortcuts remain disabled until separately modeled. Candidate graph is not native execution authority.

Native execution must read authoritative velocity after ordinary between-Post damping/flapping. One actual FlyingMoveControl tick prepares input; pure native dry travel/collision prediction precedes one real travel, under the retained exact-lease pre-move fence. Do not double-apply flapping or aiStep damping. Ground takeoff and supported landing need actual native collision evidence; accepting flight must not globally bypass ordinary noGravity/unsupported-physics guards. Preserve selected edit/revision/cache/box checks. A stable air arrival requires actual target cell, bounded target error and low speed; onGround is not required for an air goal.

Gravity cleanup is a required contract, not an implementation detail: the same native controller's WAIT branch owns restoration of ordinary gravity on stop/completion/lease release. Existing clearControls sets a current-position MOVE_TO and does not tick that branch, so it cannot be reused unchanged. Do not leave noGravity enabled, fabricate a landed state, zero native vertical motion or move the body back after cancellation. Scope any preparation/cleanup to the exact original body/controller/lease; do not touch replacement riders or controllers.

Preauthored planner cases: (1) unsupported-floor ascent/descent and horizontal detour using real Block/AStar; (2) roof clearance includes target offset and real height; (3) diagonal corner sweep rejects intersecting shapes; (4) unknown blocks, fluid cells and excluded/entity-occupied cells remain unavailable; (5) native raw node coordinates stay integral while displayed points use offset. These are graph checks only, not proof of flight equations.

Preauthored packaged cases: one NEW healthy empty bound Parrot, inspected open dry volume, original cells preserved. Take off from supported start, reach a higher air cell, detour around an actual wall, then descend to supported ground. Require real native airborne motion, unchanged inventory/health, selected-route evidence, no collision/box escape and final native noGravity false. Separately, cancel during flight and confirm owned inputs/gravity release with ordinary subsequent native motion; no position rollback or replay. First failure retains full partial outcome. Do not run against ScriptProbe or broaden to other species. Exact artifact, executor, source hash, timestamps and independent native observations are required.

Status: design/scenarios only. No guest or Java flight implementation, compilation, simulation or native execution is established by this document. Native controller parameters, authoritative arrival and cleanup still need implementation review. Flight categories outside this first mode are unfinished requirements, not exclusions.
